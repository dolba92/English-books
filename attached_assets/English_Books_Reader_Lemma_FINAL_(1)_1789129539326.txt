Но теперь pagination слишком консервативная:

- сверху/снизу и по бокам остаются слишком большие пустые области;
- даже при «Ширина текста: Широкая» и «Поля страницы: Малые» полезная область используется недостаточно.

Исправь расчёт layout/pagination так, чтобы:

- текст занимал значительно большую часть доступного Reader;
- при «Широкая» колонка реально была широкой;
- при «Малые поля» внешние поля реально были маленькими;
- сверху и снизу не резервировались огромные пустые зоны;
- на одной странице помещалось заметно больше текста;
- при этом НИ ОДНА нижняя строка не должна попадать под footer;
- нижняя строка должна иметь небольшой безопасный отступ над footer, а не огромный запас;
- количество текста должно рассчитываться по реальной доступной высоте Reader между header и footer.

ВАЖНО:
не решай проблему обрезания текста просто уменьшением количества текста на странице.
Нужно правильно рассчитывать реальную геометрию.


==================================================
1A. DESKTOP READER — ПО УМОЛЧАНИЮ ШИРОКИЙ ЭКРАН
==================================================

На ПК Reader по умолчанию должен открываться в ШИРОКОМ режиме и использовать почти всю доступную ширину окна.

То есть базовое desktop-поведение:

- широкая reading area;
- маленькие или средние внешние поля;
- заметно больше текста на одной странице;
- не 1–2 абзаца на огромном экране;
- не узкая колонка по центру с гигантскими пустыми боками;
- книга должна ощущаться как полноэкранная читалка, а не маленький текстовый блок внутри большого viewport.

DEFAULT для desktop:

Ширина текста: Широкая
Поля страницы: Малые или разумно компактные

Пользователь может сам сузить Reader через настройки:

- Узкая
- Средняя
- Широкая

То есть логика должна быть такая:

по умолчанию — максимально комфортное широкое чтение на большом экране;
если пользователь хочет более узкую колонку — он сам выбирает это в Aa Settings.

Не делай узкий Reader default.

Не рассчитывай pagination так, чтобы на большом desktop помещалось всего 2–3 небольших абзаца при обычном размере шрифта.

При стандартных desktop-настройках Reader должен использовать практически всю полезную область между левым/правым краем, с разумным max-width, и большую часть доступной высоты между header и footer.

Если viewport широкий, Reader тоже должен становиться шире в пределах комфортной длины строки.

Если viewport меньше, layout адаптивно сужается.

Главное:
ШИРОКИЙ DESKTOP READER = DEFAULT.
Узкий Reader = пользовательский выбор, а не стандартное состояние.

==================================================
2. ШИРИНА ТЕКСТА И ПОЛЯ
==================================================

Настройки должны реально заметно менять layout.

Ориентиры для desktop:

Узкая:

Средняя:

Это ориентиры, а не жёсткие значения.

При этом не растягивай текст буквально от края до края большого монитора.

4. POPUP СЛОВА У КРАЁВ ЭКРАНА
==================================================

Popup перевода должен использовать viewport-aware positioning.

Если снизу недостаточно места — открывать popup НАД словом.
Если справа не помещается — сдвигать влево.
Если слева не помещается — сдвигать вправо.

Popup никогда не должен выходить за viewport или за нижний footer.

Весь popup должен быть виден:
- английское слово;
- перевод;
- части речи;
- дополнительные значения;
- lemma, если есть;
- кнопка «В словарь».

Не меняй translation logic ради этого.

==================================================
6. НАЧАЛЬНАЯ ФОРМА / LEMMA — ГЛАВНАЯ ДОРАБОТКА
==================================================

Сохранение начальной формы уже частично работает, и это хорошо.

Например:
made -> make

Но проблема сейчас ДВОЙНАЯ:

1) Иногда определяется неправильная lemma.
Пример:
perhaps -> peharb

Так быть не должно.

2) Иногда lemma НЕ определяется вообще, хотя слово явно находится в изменённой форме.

Например:
faces должно уметь определяться как face;
dressed должно уметь определяться как dress;
heard должно уметь определяться как hear;
talking должно уметь определяться как talk;
keeping должно уметь определяться как keep;
children должно уметь определяться как child;
written должно уметь определяться как write.

На текущих скриншотах видно, что некоторые изменённые формы просто остаются без строки «Начальная форма», хотя базовую форму можно определить достаточно надёжно.

То есть задача не только «не ошибаться», но и повысить ПОКРЫТИЕ корректных форм.

7. НЕ ИСПОЛЬЗОВАТЬ ПРИМИТИВНЫЙ STEMMING

Не делай собственный примитивный stemmer.

Используй уже подключённый локальный NLP/lemma механизм и сделай его более надёжным.

Если текущая библиотека/модуль поддерживает:
- POS-aware lemmatization;
- noun singularization;
- verb base form;
- irregular forms;

Если текущий локальный модуль слишком слабый, допускается заменить ТОЛЬКО lemma-модуль на более надёжную browser-compatible English morphology/lemmatization библиотеку.

Но:

==================================================
8. ЛОГИКА ОПРЕДЕЛЕНИЯ LEMMA
==================================================

Нужен безопасный приоритет:

1. Попробовать определить lemma через надёжный локальный morphology/NLP механизм.
2. Использовать part of speech, если он уже доступен локально и его можно использовать без вмешательства в translation logic.
3. Для irregular forms использовать словарные преобразования библиотеки/морфологии.
4. Проверить, что результат является валидной английской базовой формой.
5. Если уверенности нет — оставить исходное слово.

Правило:
лучше оставить исходное слово, чем придумать несуществующую lemma.

Но для очевидных стандартных форм нужно стараться находить базовую форму, а не просто сдаваться.

==================================================
11. СОХРАНЕНИЕ В «СЛОВА»
==================================================

Если lemma определена надёжно — сохранять английское слово в базовой форме.

Примеры:

faces + перевод «лица»
-> сохранить:
face — лица

dressed + текущий перевод
-> сохранить:
dress — [уже полученный перевод]

heard + текущий перевод «слышал»
-> сохранить:
hear — слышал

made + текущий перевод «сделал»
-> сохранить:
make — сделал

КРИТИЧЕСКИ ВАЖНО:

Не отправлять lemma повторно в переводчик.
Не получать новый русский перевод для lemma.
Не заменять качественный текущий перевод.

Использовать уже полученный перевод текущего контекста.
Меняется только English-side dictionary form.

Если lemma ненадёжна — сохранить исходное слово.
